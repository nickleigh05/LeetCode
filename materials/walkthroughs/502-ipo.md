You can finish **at most `k`** distinct projects. Project `i` yields pure profit `profits[i]` and requires minimum capital `capital[i]` to start. You begin with capital `w`; finishing a project adds its profit to your capital. Return the **maximum final capital**.

```
k = 2, w = 0, profits = [1,2,3], capital = [0,1,1]  →  4
    start project 0 (needs 0) → capital 1
    now project 2 is affordable (needs 1) → capital 4

k = 3, w = 0, profits = [1,2,3], capital = [0,1,2]  →  6
```

**Constraints:** `1 <= k <= 10⁵` · `0 <= w <= 10⁹` · `1 <= n <= 10⁵` · `0 <= profits[i] <= 10⁴` · `0 <= capital[i] <= 10⁹`

> **Try it yourself first.** The sections below go from a gentle nudge to the full answer — open only as far as you need, then go back and try again.

<details>
<summary><b>1 · Scan the problem</b> — what the words are telling you</summary>

| The statement says | Which really means |
|---|---|
| "**at most `k`** projects" | A budget on *count*, not on capital |
| profit is **pure** and added to capital | ⚠️ Capital only ever **grows** — so the affordable set only ever **expands** |
| capital requirement per project | Affordability is a moving threshold |
| `profits[i] >= 0` | ⚠️ No project ever loses money, so there's never a reason to decline a free profit |
| `n`, `k` up to 10⁵ | O(k · n) = 10¹⁰ is far too slow |

**The greedy, and why it's safe.** At each step:

> Among all projects you can **currently afford**, pick the one with the **highest profit**.

Two facts make this optimal:

1. **Profits are non-negative**, so taking any affordable project never hurts — your capital can only rise.
2. **Capital never decreases**, so a project affordable now stays affordable forever. Deferring it costs nothing; taking a *smaller* profit now to "save" a bigger one for later gains nothing, because the bigger one remains available.

So there's no trade-off across time — the maximum-profit affordable project is always the right choice. (Contrast a knapsack, where taking one item genuinely forecloses another.)

**The structural challenge: two different orderings.**

- To know **what's affordable**, you need projects sorted by **capital ascending**
- To pick **the best affordable one**, you need them ordered by **profit descending**

One data structure can't efficiently serve both. The answer is to use **two**:

```
projects sorted by capital  ──unlock──▶  max-heap of profits  ──pick──▶  best
      (a pointer sweeps                     (only affordable
       forward as w grows)                   projects live here)
```

**The two-structure dance:**

1. Sort projects by capital; keep an index `i` into that sorted list
2. Move every project with `capital <= w` into a **max-heap keyed on profit**
3. Pop the largest profit, add it to `w`
4. Repeat `k` times — the increased `w` may unlock more projects in step 2

🤔 **Before you open the next section:** since capital only grows, what happens to a project once it becomes affordable — and why does that mean the pointer never moves backward?

</details>

<details>
<summary><b>2 · Choose the tool</b> — the options, and why one wins</summary>

| Approach | How it works | Time | Space | Verdict |
|---|---|---|---|---|
| Scan all projects each round | Find the best affordable one linearly | O(k · n) | O(1) | ❌ 10¹⁰ operations |
| Sort by profit, scan for affordable | Re-scan each round | O(k · n) | O(n) | ❌ Same bound |
| **Sort by capital + max-heap of profits** | Unlock, then pick | **O(n log n + k log n)** | O(n) | ✅ |

**The decision: sort by capital, sweep a pointer, and maintain a max-heap of unlocked profits.**

**Why the pointer only moves forward** — this is what makes it efficient:

Capital is non-decreasing (profits are ≥ 0), so once `capital[i] <= w` holds, it holds forever. The sorted-by-capital list can therefore be consumed **monotonically**: each project is unlocked exactly once, across the whole run, and never re-examined.

That's the same amortized argument as a sliding window's left pointer — the inner `while` loop looks nested, but its total iterations across all `k` rounds are bounded by `n`.

**Why a max-heap for profits.** Once unlocked, projects sit in a pool where you repeatedly need the maximum. Sorting the pool would go stale as new projects join; a heap handles insertion and max-extraction in O(log n) each.

Python's `heapq` is a min-heap, so push `-profit` and negate on extraction.

**Why you can stop early.** If the heap is empty at the start of a round, no project is affordable — and since `w` can't grow without completing a project, none ever will be. Break out; further rounds are pointless.

**Why sorting by capital rather than profit.** You need the *affordability frontier* in order, so that the pointer sweep is monotonic. Sorting by profit would mean rescanning for affordability every round — back to O(k·n).

**Why not a single sorted structure?** You'd need something ordered by capital for unlocking *and* by profit for selection. A balanced BST keyed on profit with capital-based bulk insertion could work, but two simple structures — a sorted array plus a heap — are clearer and equally fast. **This "sort by one key, heap on another" pairing is the reusable idea.**

</details>

<summary><b>3 · Build the code</b> — block by block</summary>

```python
import heapq

projects = sorted(zip(capital, profits))
```

**Pair each project's capital with its profit, sorted by capital ascending.**

`zip` builds `(capital, profit)` tuples; `sorted` orders by the first element, which is exactly the affordability order the pointer sweep needs.
→ [zip-function](../syntax/zip-function.md) · [sorting-key](../syntax/sorting-key.md)

```python
max_heap = []
i = 0
n = len(projects)
```

- `max_heap` — profits of **currently affordable** projects (negated for max behaviour)
- `i` — how far into the sorted list we've unlocked; **only ever increases**

→ [heapq-module](../syntax/heapq-module.md)

```python
for _ in range(k):
    while i < n and projects[i][0] <= w:
        heapq.heappush(max_heap, -projects[i][1])
        i += 1
```

**Unlock everything now affordable.**

`projects[i][0]` is the capital requirement, `[1]` the profit. Push the **negated** profit so the max-heap behaves correctly.

`i` never resets, so across all `k` rounds this inner loop runs at most `n` times **in total** — that's what keeps the algorithm efficient despite the nesting.
→ [while-loop](../syntax/while-loop.md) · [logical-operators](../syntax/logical-operators.md)

```python
    if not max_heap:
        break
```

**Nothing affordable → stop.**

Capital only grows by completing projects, so if none are available now, none ever will be. Breaking here is both an optimization and what prevents popping from an empty heap.
→ [break-continue](../syntax/break-continue.md)

```python
    w -= heapq.heappop(max_heap)
```

**Take the most profitable affordable project.**

`heappop` returns the most negative value — the largest real profit. Subtracting a negative **adds** it to `w`, which is a compact way to undo the negation.

Written out: `w += -(heapq.heappop(max_heap))`. The `-=` form is idiomatic once you're used to negated heaps, but be deliberate about it.
→ [heapq-module](../syntax/heapq-module.md) · [arithmetic-operators](../syntax/arithmetic-operators.md)

```python
return w
```

<details>
<summary>The whole thing together</summary>

```python
import heapq

class Solution:
    def findMaximizedCapital(self, k: int, w: int, profits: List[int], capital: List[int]) -> int:

        projects = sorted(zip(capital, profits))

        max_heap = []
        i = 0
        n = len(projects)

        for _ in range(k):
            while i < n and projects[i][0] <= w:
                heapq.heappush(max_heap, -projects[i][1])
                i += 1

            if not max_heap:
                break

            w -= heapq.heappop(max_heap)

        return w
```

</details>

**Trace it** — `k = 2`, `w = 0`, `profits = [1,2,3]`, `capital = [0,1,1]`:

**Sorted by capital:** `[(0,1), (1,2), (1,3)]`

| Round | `w` before | Unlocked (capital ≤ w) | Heap (real profits) | Popped | `w` after |
|---|---|---|---|---|---|
| 1 | 0 | `(0,1)` → push 1 | `[1]` | **1** | **1** |
| 2 | 1 | `(1,2)`, `(1,3)` → push 2, 3 | `[3, 2]` | **3** | **4** |

Return **4** ✅

Round 2 shows both mechanisms: raising `w` to 1 unlocked **two** new projects, and the heap surfaced the better one (3 over 2) without any scanning.

**The second example** — `k = 3`, `w = 0`, `profits = [1,2,3]`, `capital = [0,1,2]`:

Sorted: `[(0,1), (1,2), (2,3)]`

| Round | `w` before | Unlocked | Heap | Popped | `w` after |
|---|---|---|---|---|---|
| 1 | 0 | `(0,1)` | `[1]` | 1 | 1 |
| 2 | 1 | `(1,2)` | `[2]` | 2 | 3 |
| 3 | 3 | `(2,3)` | `[3]` | 3 | **6** |

Return **6** ✅ — each round's profit unlocked exactly the next project.

**An early-break case** — `k = 5`, `w = 0`, `profits = [5]`, `capital = [10]`: round 1 unlocks nothing (`10 > 0`), the heap is empty, so we break immediately and return **0**. Without the break, `heappop` on an empty heap would raise `IndexError`.

<details>
<summary><b>4 · Time complexity</b> — O(n log n + k log n)</summary>

**O(n log n + k log n)**.

| Phase | Cost |
|---|---|
| Sorting by capital | **O(n log n)** |
| Unlocking (total across all rounds) | **O(n log n)** — each project pushed once, O(log n) each |
| Selection | **O(k log n)** — one pop per round |

At `n = k = 10⁵`: `10⁵ × 17 × 2` ≈ **3.4 × 10⁶ operations** — fast.

**The amortized point worth stating aloud:** the inner `while` sits inside a `for` loop, which *looks* like O(k · n). It isn't — `i` only moves forward and never resets, so across the entire run the inner loop executes at most `n` times **in total**.

That's the same accounting as the sliding-window and monotonic-stack problems: **a nested loop with a global work budget.**

**Compare to the naive approach:** scanning all projects each round is O(k · n) = 10¹⁰. The sort plus heap converts "search for the best affordable project" into "maintain a pool and take its max."

**Early termination** can cut this substantially — if capital stalls, the break fires immediately regardless of how large `k` is.

</details>

<details>
<summary><b>5 · Space complexity</b> — O(n)</summary>

**O(n)** — the sorted `projects` list plus a heap holding at most `n` profits.

The heap can grow to hold every project if all become affordable, so O(n) is the honest bound.

| | Space |
|---|---|
| Sorted pairs | O(n) |
| Max-heap | O(n) worst case |
| Pointer, capital | O(1) |

**Could you avoid the sorted copy?** You could sort indices instead of building tuples, saving a constant factor but not an order. Sorting `zip(capital, profits)` is clearer and the allocation is one-time.

**The design idea worth extracting:**

> **When selection needs one ordering but availability needs another, use two structures: sort by the *availability* key and sweep a monotonic pointer, then heap on the *selection* key.**

The sort handles a static ordering that never changes; the heap handles a dynamic pool that grows as constraints relax. Neither alone suffices.

The same pairing solves [Single-Threaded CPU](1834-single-threaded-cpu.md) — sort by enqueue time, heap by processing time — and [Maximum Subsequence Score](2542-maximum-subsequence-score.md), which sorts by the minimum-constraint key and heaps on the summed key.

</details>

<details>
<summary><b>6 · Talk it through</b> — trade-offs & follow-ups</summary>

**Say this out loud:**

> "Profits are non-negative and capital only grows, so a project that's affordable now stays affordable forever — which means there's no reason to defer anything, and the greedy of always taking the highest-profit affordable project is optimal. The difficulty is that affordability is ordered by **capital** while selection is ordered by **profit**, and one structure can't serve both. So I sort the projects by capital and sweep a pointer forward, pushing each newly affordable project's profit into a max-heap. Each round I unlock whatever the current capital allows, then pop the largest profit and add it. The pointer never resets, so the inner loop runs at most `n` times across the whole run — it's O(n log n) for the sort plus O(k log n) for the selections, not O(k·n). If the heap is ever empty I break, since capital can't grow without completing a project."

**Follow-ups you should expect:**

| If they ask… | Answer |
|---|---|
| "Why is the greedy optimal?" | **The key argument.** Profits are ≥ 0 and capital never decreases, so an affordable project stays affordable — deferring costs nothing, and taking the maximum now never forecloses a better option. |
| "Why isn't the nested loop O(k·n)?" | The unlock pointer only moves forward and never resets — total inner iterations ≤ n. |
| "What if profits could be **negative**?" | The greedy breaks — you might decline a project. It becomes a genuine optimization problem, potentially DP. |
| "What if completing a project **consumed** its capital?" | Capital could decrease, so affordability isn't monotonic and the pointer sweep is invalid. Much harder. |
| "Why sort by capital rather than profit?" | You need the affordability frontier in order so the sweep is monotonic. Sorting by profit forces a rescan each round. |
| "Why the empty-heap break?" | Capital only grows via completed projects, so if nothing is affordable now, nothing ever will be — and popping empty would raise. |
| "Can you avoid the sort?" | Not really — you need capital order. A heap keyed on capital would work but adds a second heap for no gain. |

**Traps:**

- **Scanning all projects each round.** O(k·n) = 10¹⁰.
- **Resetting the unlock pointer each round.** Turns the amortized O(n) into O(k·n) and re-pushes duplicates.
- **Forgetting the empty-heap break.** `IndexError` when nothing is affordable.
- **Getting the negation wrong.** `w -= heappop(...)` adds the profit because the stored value is negative; writing `w += heappop(...)` subtracts it.
- **Sorting by profit.** Breaks the monotonic unlock.
- **Assuming you must complete exactly `k` projects.** It's *at most* `k` — the break handles finishing early.
- **Pushing the whole tuple into the heap.** You'd order by capital again; push only the negated profit.
